Goal

Ship an on-device AI Coach in the floating navbar — Vercel AI SDK agent loop and tools running inside the app, talking DIRECTLY to OpenRouter with the user's own key and their chosen model from OpenRouter's live catalog, with no server component of any kind — and move Exercises out of the navbar behind a home-header icon with a clickable `workouts/exercise` breadcrumb.

Assumptions

  • HEADLINE DECIDED — Option A: on-device Vercel AI SDK (ai-sdk.dev), direct to OpenRouter. Tools and agent logic are defined inside the app; the user supplies their own OpenRouter key and picks the model. Option B (eve on Vercel) is REJECTED: eve is coupled to a Vercel-deployed server that serves the agent requests — it is more like a serverless framework — which is the wrong SHAPE for an in-app agent. eve's genuine future triggers (server-side code execution, cron nudges with the app closed, cross-device sync) are preserved in Out of Scope as the documented re-evaluation trigger.
  • TRANSPORT DECIDED — direct, no relay. There is NO server component at all. The former T16 (Cloudflare relay on workers/strava-proxy) is DELETED, along with the `transport` field, the proxied/direct split, the `directJustification` type, the worker upstream map, worker-side log scrubbing, and the relay sentinel test.
  • PROVIDER SET DECIDED — OpenRouter only. This is what kills the relay: the Anthropic / OpenAI / Google client-key prohibitions are INAPPLICABLE (not overridden) because the app never touches those providers' keys. The user holds ONE OpenRouter key and OpenRouter fans out to models. The entire prior provider-ToS section is SUPERSEDED and moot.
  • OpenRouter ToS position, stated honestly and NOT overclaimed — NO PROHIBITION FOUND, but not explicit permission. The terms contemplate "the extent you incorporate the Service into your own products and services" and place key confidentiality on the user; they do NOT explicitly bless mobile or client-side use; and they DO prohibit "reselling API access to Models or otherwise developing a competing service" (openrouter.ai/terms). BINDING CONSTRAINT: the app must never pool or resell access — every call uses the end user's own key.
  • OAuth PKCE CONFIRMED: `https://openrouter.ai/auth?callback_url=&code_challenge=&code_challenge_method=S256`, exchanged at `POST https://openrouter.ai/api/v1/auth/keys`, yielding "a user-controlled API key" that is revocable and credit-limitable, with no client registration or client secret documented. UNCONFIRMED: whether a custom scheme (expo-linking `myapp://`) is accepted as `callback_url`. HARD REQUIREMENT: the app must NOT ship a hardcoded model list. The axis of variation is no longer providers, it is MODELS, and OpenRouter's live catalog is the binding layer.
  • Tool calling CONFIRMED normalized: "OpenRouter standardizes the tool calling interface across models and providers"; non-native providers get tools mapped or "transform[ed] into a YAML template". Reliability nonetheless VARIES per model — the tools-only catalog filter is necessary but not sufficient.

  • The OpenRouter key lives in expo-secure-store ONLY — never SQLite, never app.config extra, never a React Query cache key, never a Sentry payload. It leaves the device solely as the Authorization header on a request to OpenRouter. With no relay, no worker and no server, client telemetry is the ENTIRE scrubbing boundary.
  • Exercises stays a file inside `app/(tabs)/` and stays a registered Tabs.Screen; it leaves the navbar purely by dropping out of TAB_ORDER. No file move, no route-group migration, no deep-link breakage.
  • Schema changes are hand-written phased DDL (`lib/db/tables.ts` createExtensionTables + `lib/db/migrations.ts` phase 2), mirrored in `lib/db/schema.ts`. This repo does NOT use drizzle-kit generated migrations.
