AI Coach gym-photo workout drafts

Generated: 2026-06-06

Goal

Let a CableSnap user upload a gym photo in AI Coach, receive a model-verified equipment detection and a locally deterministic, auditable workout draft, revise or restore it conversationally, and intentionally open its new workout session from a rich card—without persisting the photo or automatically navigating away from chat.

Assumptions

  • Scope classification: Complex. This crosses native media permissions, a BYOK multimodal AI boundary, SQLite migration/backup compatibility, deterministic training rules, tool safety, chat rendering, navigation, and live verification. This artifact is planning-only; product source code is not changed.
  • Current coach path: app/(tabs)/ai-coach.tsx provides CoachConversation; CoachConversation persists the user turn through useAppendCoachMessage, starts startCoachAgent with coachTools, and renders persisted tool calls. lib/ai/agent.ts currently accepts only text ModelMessage content and gates every selected model on the OpenRouter catalog's tools parameter.
  • Current persistence is SQLite/Drizzle: coach_messages has text content, model_id, tool_calls, created_at and error (lib/db/schema.ts:449-461); extension table creation is in lib/db/tables.ts:278-299; additive upgrades are in lib/db/migrations.ts; backups currently include coach_sessions and coach_messages in the AI Coach category (lib/db/import-export.ts:22-181).
  • Current model fact, externally observed on 2026-06-06: OpenRouter's NVIDIA Nemotron 3 Ultra free model page describes text input/output and tool calling, but does not advertise image input; it explicitly says response_format is unsupported. Therefore nvidia/nemotron-3-ultra-550b-a55b:free is not an eligible gym-photo model unless the live catalog later reports both tools and image input. It remains an acceptable text-only coach model.
  • Conservative default: a gym photo is resized/re-encoded locally to a bounded JPEG before direct BYOK transmission, is deleted from temporary storage after request completion/abort, and is never written to coach_messages, workout drafts, backups, analytics, Sentry breadcrumbs, or model/tool logs. The persisted user turn says only that a gym photo was uploaded.
  • Conservative default: initial draft creation and every successful revision are local, durable revision writes; no workout session/template is started or navigated to until the user taps the rendered draft card. This favors recoverability and fulfills 'save it and continue updating afterward.'
  • Conservative default: the AI may classify visible equipment and select a constrained mutation tool, but it never calculates the workout. A local deterministic engine reads only allowlisted local history/context and emits the exercise, dosage, load guidance, duration estimate, and reason ledger used by the card.
  • User-approved MVP time rule: if the user says morning/short/limited time, start from a 30-minute target and adjust it only by the median duration of the latest up-to-eight completed workout sessions when that median stays within the defined 20–45 minute safe bound; otherwise retain 30 minutes. Without a limited-time request, use that median clamped to 30–60 minutes, falling back to 45 minutes. The visible reason ledger states the source, adjustment, bound, or fallback.
  • Conservative default safety rule: choose active library exercises compatible with detected equipment; prefer recently/frequently completed exercises and their last successful working sets. For unfamiliar equipment or no comparable history, prescribe an RPE 6–7 familiarization set and 'start light; adjust after a controlled first set,' not a confident numeric weight.
  • Repository governance advisory: before P2 programming/recovery/load rules are finalized or implemented, run this repository's mandatory .claude/skills/review--sports-science review (including its Perplexity research step unless network is unavailable), record its APPROVE / APPROVE_WITH_CHANGES / NEEDS_RESEARCH / REJECT verdict and incorporated advisory changes in this HTML artifact, and treat it as CEO-facing domain input rather than a hard release gate. This planning-stage governance SKILL is distinct from runtime AI SDK coach tools: it is never imported into the app, registered in lib/ai/tools/index.ts, sent to OpenRouter, or callable by the model.
  • No new backend, provider account, computer-vision SDK, or unrelated architecture migration is in scope. Existing expo-image-picker, expo-image-manipulator, expo-file-system, AI SDK/OpenRouter provider, Zod, SQLite, React Query, Card, and router patterns are reuse points.

Success Criteria

  • Photo intake: with valid permission, consent, a fresh catalog record advertising tools + image input, and a supported image, exactly one bounded re-encoded image is sent directly to the selected OpenRouter model; only '[Gym photo uploaded]' (or equivalent neutral marker) is persisted. Unsupported/cancelled/denied/oversize/processing-failed inputs send zero image requests and retain the chat.
  • Model compatibility: OpenRouter catalog parsing exposes validated input modality capability. A photo can never be sent merely because a model is free, named Nemotron, or supports tools. The observed Nemotron 3 Ultra free configuration is rejected for photo until live catalog evidence says otherwise; ordinary text coaching still works with it.
  • Equipment and determinism: the model supplies only validated equipment labels; local deterministic logic produces the draft from detection plus bounded local last-workout, pattern, duration, recovery/rested-muscle, exercise-library, and performance context. Limited-morning requests start at 30 minutes and use the historical median only within the defined 20–45 minute safe bound. Same inputs/clock produce same canonical draft/reason ledger; empty/ambiguous detection yields clarification rather than fabricated equipment.
  • Workout safety: planned exercises exist in the active local library and are equipment-compatible. History-based loads are only shown where comparable completed working-set data exists. Novel/unfamiliar equipment says start light/RPE 6–7 and explains why; the feature neither diagnoses nor makes medical claims.
  • Card and navigation: a successful draft renders detected equipment, duration, ordered exercise prescription, safe load guidance, saved revision, and card-following auditable reasons. It never redirects due to generation/reload/stream completion. One deliberate card press atomically creates one uncompleted workout session then navigates to its existing session screen.
  • Conversation and versioning: text changes use narrow validated operations, append saved revisions, render updated card/reasons, and survive chat reload/selection. Historical revision restoration appends a new latest state and permits later modifications; stale expected revision does not overwrite data.
  • Data/privacy: no raw image, URI, base64, EXIF, location, face/body inference, API key, or provider response secret persists or is logged/exported. One-time explicit consent and persistent nearby disclosure explain direct third-party BYOK processing, possible gym background/people sensitivity, and opt-out/cancel; all failures are actionable and do not leak sensitive values.
  • Verification: targeted Jest, mocked browser E2E, backup E2E, typecheck, lint, localization check, and a key-gated live tools+image model proof all exit 0. The live proof must show current catalog capability plus real structured result; it is not satisfied by the current Nemotron text/tool probe.

Out of Scope

  • Automatic workout start/navigation, camera capture, background processing, multi-photo albums, photo history/gallery, durable photo storage, or attachment reuse across turns.
  • Person/face recognition, physique/body-fat/injury analysis, medical advice, exercise-form diagnosis, and any inference unrelated to visible equipment.
  • Cloud accounts, backend relay, shared/social plans, provider/model purchase management, or static model allowlists.
  • Redesigning existing session editing, template/program systems, the global AI Coach architecture, existing prompt streaming, or unrelated dependency/security upgrades.

Risk Flags

  • Provider capability data may be incomplete or change: mitigate by parsing live modality fields, requiring fresh preflight for photo, displaying a compatible-model recovery, and failing live verification on mismatch rather than guessing.
  • Free providers are volatile and the observed Nemotron free model is text-only: mitigate with explicit env-selected real vision+tool test model, existing typed provider/rate-limit recovery, and no automatic downgrade that would send a photo to an incompatible model.
  • Photo privacy is high impact: mitigate by first-use disclosure, local re-encode stripping metadata, hard byte/dimension cap, memory/cache cleanup on every path, redaction tests, no durable photo state, and non-personal live fixture only. OpenRouter's Nemotron free page itself warns against confidential/personal uploads, so UI must not imply a provider is private.
  • Vision detection is probabilistic: mitigate with a closed equipment vocabulary, confidence/uncertainty display, user clarification path, active-library validation, and deterministic plan generation rather than trusting model-written routines.
  • Draft/revision writes can race through retries or concurrent chat turns: mitigate with expected latest version, transactionally appended immutable revisions, idempotency/request identifiers where needed, and explicit conflict/reload recovery.
  • Direct session creation can leave partial rows or duplicate starts: mitigate with one transaction, card-level pending state/debounce, post-write verification, route only after durable success, and query-version invalidation.
  • Chat bubble/card composition may regress mobile layout and existing Markdown semantics: mitigate with structured tool-result parsing isolated to successful draft tools, legacy fallback, test IDs/a11y, existing viewport regression suites, and no global markdown parser change.
  • Backup schema expansion can break imported historical data: mitigate with additive tables, migration tests, child-after-parent import order, dynamic-column legacy tolerance, and v8 regression fixture coverage.
